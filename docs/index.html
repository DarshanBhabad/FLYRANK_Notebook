Ranking Refresh Opportunities — Capstone Paper

Abstract

This project builds a practical ranked review engine that helps editors prioritize which content pages to review for refresh or metadata fixes. Using the FlyRank internship starter dataset (30,000 anonymized content rows) I frame the decision, build a transparent baseline score, and compare simple learned models to the rule baseline. The best models and the rule are validated with client-aware splits and top-K metrics (precision@K) so the output maps directly to an editor's capacity. The repo contains reproducible notebooks and the ranked action queue; a public-safe playbook turns model outputs into human review actions.

Introduction / Problem statement

Decision supported: which pages should a content editor review first (refresh, title/meta rewrite, monitor, or prune) given limited review capacity. The actor is the content/editor team; the action is a human review and targeted update. A wrong recommendation wastes editorial time (false positives) or misses high-impact pages (false negatives). The goal is a ranked queue that maximizes precision@K for the top pages the team can realistically review.

Data

  • Starter slice used here: data/raw/content_refresh_anonymized.csv (30,000 rows × 44 columns). This public starter snapshot is included in the repository. The full warehouse release is FlyRank/internship-warehouse on Hugging Face (gated).
  • Date windows and tables used: starter CSV is a snapshot with trailing 90-day aggregates; full-work runs on fact_content_daily_performance partitioned by month for production-scale validation.
  • Exclusions: product decision flags and derived outputs like priority_score or health_score are excluded. trend_direction and trend_pct are not used as features because they are label-derived and cause leakage.

Methodology

Lane chosen: Refresh / Content Opportunity Scoring — a ranked action queue with reason codes.

Features (examples used in the notebooks): impressions_90d (visibility), ctr, avg_position, days_since_last_update (freshness), word_count, ai_sessions_90d (sparse). Each feature is justified as knowable at decision time.

Label / proxy: the starter target is is_declining_label (derived from trend_direction == 'down'), used here for pipeline demonstration. For honest future-window prediction, build prior->future labels and enforce leakage control.

Baseline: a transparent rule-based baseline score (work/notebooks/w04_baseline_score.ipynb) combining visibility, freshness risk, and a position opportunity term into a single score with reason codes: stale_visible_page, low_ctr_visible_page, monitor.

Validation: client-holdout splits and precision@K for top-50/top-100 review cycles. The notebooks include leakage checks and a controlled demo showing how trend-derived fields leak the label.

Results (summary)

  • Starter dataset: 30,000 rows; is_declining_label prevalence ≈ 54% (16,262 rows after prep).
  • Reference starter results: logistic regression ROC AUC ≈ 0.70, random forest ROC AUC ≈ 0.75 (see the repo outputs for exact numbers).
  • The rule baseline is computed in work/notebooks/w04_baseline_score.ipynb and a ranked CSV is written for reviewer inspection. Top-K reviews and manual checks are recorded in the notebooks.

Limitations & honest framing

  • Observational only: decision-support, not causal proof.
  • Unbalanced panel and GA4 availability differ by client; use per-client windows and volume filters.
  • AI referral signals are sparse; treat them as EDA/ranking only.

Ranked recommendations (action playbook)

Output: a ranked CSV with content_id, client_id, baseline_score, reason_code, action. Reason codes: stale_visible_page (review_refresh), low_ctr_visible_page (review_ctr), monitor. Use precision@K to pick review capacity.

Reproducibility

Notebooks: work/notebooks/w01–w04 and supporting scripts. Run python scripts/run_all.py for the starter pipeline. Full-warehouse work requires HF_TOKEN and access to the gated Hugging Face dataset.
